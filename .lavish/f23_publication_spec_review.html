Publish exactly what the developer approved.

F23 turns a final Review Bundle into a durable publication workflow: fresh exact-diff verification, one explicit approval, non-force code publication, independently reconciled responses, and a truthful terminal outcome.

Publication path

Every arrow crosses a durable boundary. If evidence becomes uncertain, the flow moves to recovery/attention; it never silently starts a second effect.

Non-negotiable guardrails

  • fresh SHAExact head repository/ref and expected old SHA must still match.
  • complete diffOnly the proposed-worktree diff relative to worktreeBaselineSha is publishable.
  • no forceNon-force push only; no automatic rebase or target substitution.
  • response ledgerEach included response gets its own pending/posted/failed/unknown record.
  • no AI authorityAI can review or edit locally, never commit, push, or post.

Durable effect progress

01 · PENDING

Approval and publication intent are committed before side effects.

02 · COMMIT_CREATED

Exact local commit and candidate tree are recorded.

03 · NO_CODE_CHANGE

Empty code diff means no empty commit or push.

04 · PUSHED

Remote destination ref equals the recorded commit SHA.

05 · RESPONSES_PENDING

Selected replies are being posted or reconciled independently.

06 · COMPLETED

Bundle is PUBLISHED and the hold can release.

07 · UNKNOWN

Possible effect needs deterministic inspection; no blind retry.

08 · FAILED

Pre-effect failure remains held and offers a safe next action.

Implementation slices

Slice 1

Candidate + approval

Show complete diff, SHAs, target, validation, commit message, and response plan. Lock only after explicit approval.

Slice 2

Preflight + intent

Refresh F06/F13/F14/F22 evidence, reject stale/unsafe state, then persist the idempotency-bound intent.

Slice 3

Code staging

Stage the exact candidate; support no-code and one-commit paths without touching the developer clone.

Slice 4

Non-force push

Push to the exact PR head repository/ref with expected-old-SHA protection and remote verification.

Slice 5

Response ledger

Post selected replies only after code/no-code is reconciled; recover each response independently.

Slice 6

Terminal outcome

Publish or publish-with-errors, preserve history, finalize handled versions, and release the hold once.

Response inclusion tradeoff

Per-response Include / Exclude Draft choice

  • Decline one reply while publishing the approved code.
  • Matches the independent retry ledger and partial-failure model.
  • Requires one more explicit decision per response.

All edited responses together

  • Simpler approval surface and fewer controls.
  • Cannot omit a single response without editing/reviewing again.
  • Still needs independent effect state for uncertain recovery.

Risks to resolve early

Remote ambiguity

GitHub response APIs may not expose an idempotency key; ambiguous matches stay UNKNOWN rather than risking a duplicate.

Dirty worktree

Un-attributed changes require acknowledgement of the complete current diff; overlap and unknown state block publication.

State separation

F02 domain phases and application effect progress must remain two views of one publication, not competing machines.
