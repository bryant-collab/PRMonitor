# Plan: F00 Deterministic Validation Configuration Contract

> **Document status:** Architecture-stage draft | Active implementation PLAN
>
> **Owning PRD:** `F00_deterministic_validation_configuration_contract_PRD.md`
>
> **Last revalidated against:** `Specs/application_overview.md` revision 2026-09-19 and F00 PRD revision 2026-09-19
>
> **Entry/readiness gates:** No product-feature dependency. The existing Node.js/TypeScript workspace and root npm scripts must still pass before work starts. No Electron, SQLite, renderer, worktree manager, or production process runner is required for F00.

## Implementation Boundary

F00 implements the reusable, deterministic contract rather than the production validation runner. Add a new framework-neutral workspace package, proposed as `packages/validation-contract`, containing Zod-first schemas, generated JSON Schema, canonical normalization/hashing, source resolution, authorization checks, path-policy helpers, output-bound/redaction primitives, run-state aggregation, and conformance fixtures. F01 incorporates the package into the application workspace; F03 persists its records; F14 supplies real child-process execution and process-tree termination; F16 supplies configuration UI.

Do not add Electron, React, SQLite, Git commands, an AI SDK, automatic command discovery, or live process spawning in this feature. If implementing the contract reveals a product contradiction, update the PRD and rerun both specification linters before continuing.

## Proposed Vertical Slices

1. **Parse, normalize, and resolve one effective validation profile.**
   - **Blocked by:** None.
   - **Stories / requirements / acceptance criteria:** US-01-US-03; FR-01.1-FR-01.7; NFR-02; NFR-04-NFR-06; AC-01; AC-14.
   - **Implementation:** Add the `packages/validation-contract` workspace with a Zod-first version-1 profile schema and exported TypeScript types. Model ordered commands as `executable` plus `arguments`, relative working directory, default/effective timeout, per-stream output limit, and stable ID/label. Model each manual check as a separate tagged step requiring its own stable ID, display label, and instructions; its serialized and display-summary forms carry `kind: manual`, while commands carry `kind: command`, so consumers can visibly distinguish them without guessing from fields. Generate and commit `Specs/contracts/validation-profile.v1.schema.json` from the schema. Implement a pure resolver that accepts optional one-run, saved, and checked-in candidates, validates each applicable candidate, and returns exactly one of `ready`, `confirmation_required`, `invalid`, or `unavailable` without merging profiles. `schemaVersion: 1` is dispatched to a version-specific parser and every unsupported value is rejected. Future additive contract versions must add a new version-specific parser/JSON Schema and preserve the version tag and original meaning of stored snapshots; they may not reinterpret version-1 records. Unknown version-1 keys are rejected so configuration typos cannot silently change behavior. The resolver has no manifest, build-file, documentation, AI-history, or process-history discovery input, and conformance tests prove those files cannot implicitly create a profile or command.
   - **Visible result:** Developers can inspect one committed JSON Schema and example profile, and the conformance test output identifies the selected source or an exact field error.
   - **Durable records / external effects:** Adds source files, generated JSON Schema, fixtures, and workspace metadata only. It does not execute repository code or create runtime state.
   - **Failure / cancellation / restart:** Unsupported versions, duplicate IDs, empty profiles, invalid bounds, absolute/traversing working directories, and malformed candidates resolve to deterministic errors. There is no runtime operation to cancel or resume.
   - **Exact evidence:** Schema-generation drift test; table-driven parse failures; manual-step tests requiring stable ID/label/instructions and preserving the visible `manual` discriminator in serialized confirmation summaries; version-dispatch tests accepting version 1, rejecting unknown versions, and proving a stored version-1 snapshot round-trips unchanged through the compatibility reader; precedence matrix covering every source combination; property test proving source commands are never merged; negative discovery fixtures containing tempting `package.json`, build-file, README, AI-output, and process-history commands that still resolve to `NO_PROFILE`; example-profile validation; root `npm run check`.
   - **Exit criterion:** AC-01 and AC-14 pass; `FR-01.1` through `FR-01.7` are represented in the public schema/API; generated schema is reproducible.

2. **Bind human authorization to normalized profile meaning.**
   - **Blocked by:** Slice 1.
   - **Stories / requirements / acceptance criteria:** US-01-US-03; FR-02.1-FR-02.7; NFR-01-NFR-02; NFR-05; INV-02; INV-07; AC-02-AC-04.
   - **Implementation:** Add canonical JSON normalization after defaults, SHA-256 content hashing, repository identity, approval records, and one-run authorization records. Implement pure trust evaluation for saved, checked-in, and one-run sources. Require matching repository/source/schema/hash; bind one-run authorization to an operation ID; return explicit confirmation content including executable, arguments, work directory, timeout, limits, manual checks, and the repository-code/no-OS-sandbox warning. Represent AI proposals only as untrusted candidate profiles; the contract exposes no method that marks them trusted without an authorization record. Approval deliberately excludes local clone path, branch, pull-request ID, and process instance, so changing only one of those values or restarting the application preserves approval when repository identity, source, schema version, and normalized content hash are unchanged.
   - **Visible result:** A command-line fixture report shows the exact profile summary a future UI must display, whether it is trusted, why it is not trusted, and which user action can authorize it.
   - **Durable records / external effects:** Defines serializable approval/authorization records. Persistence is deferred to F03. No external process or AI provider is invoked.
   - **Failure / cancellation / restart:** A one-byte semantic change produces a new hash and `confirmation_required`; whitespace/key-order-only changes retain the normalized hash; repository or operation mismatch fails closed; restart-compatible serialized approval fixtures produce the same decision.
   - **Exact evidence:** Golden canonicalization vectors; hash-change/hash-stability tests; repository/source/schema/hash mismatch table; unchanged-content matrix across clone-path change, branch change, pull-request change, and application restart; one-run operation-expiry test; AI-proposal-is-untrusted compile/runtime test; confirmation-summary snapshot with secret-free sample values.
   - **Exit criterion:** AC-02, AC-03, and AC-04 pass; no public API can convert a candidate into trusted configuration without explicit authorization evidence.

3. **Define the worktree-confined execution and lifecycle state machine.**
   - **Blocked by:** Slices 1-2.
   - **Stories / requirements / acceptance criteria:** US-04; US-06; FR-03.1-FR-03.6; FR-04.1-FR-04.8; NFR-01-NFR-03; NFR-06; INV-01-INV-04; INV-06-INV-07; AC-05-AC-07; AC-10; application criteria APP-AC-13, APP-AC-48, APP-AC-49, and APP-AC-57.
   - **Implementation:** Define runner-neutral prepared-command, step-state, run-state, and closed reason schemas. Add a path-policy function that accepts a canonical operation-worktree root and a canonicalized candidate directory from a filesystem adapter, requiring containment and directory existence immediately before launch. Add effective timeout calculation that defaults an omitted timeout to 600 seconds, accepts inclusive values from 1 through 3,600 seconds, rejects values outside that range, and copies the effective value into confirmation and snapshot records. Add sequential/stop-on-first-nonpass transition rules, legal lifecycle transitions, and restart finalization. Implement a runner-neutral termination coordinator that, for timeout or cancellation, requests graceful termination of the complete process tree through a process-control port, waits exactly five seconds on an injected clock, force-terminates any reported survivors, and only then finalizes the `interrupted` evidence. Specify a future runner port that only accepts structured executable/argument commands, controlled environment data, and a persisted immutable snapshot; it exposes no shell-string entry point. The preparation result includes the executable resolved through controlled `PATH`/Windows `PATHEXT` handling and requires the future runner to record that resolved path without invoking a shell. The version-1 profile schema contains no environment or secret fields, rejects attempts to add them, and the controlled-environment policy removes GitHub credentials, AI-provider credentials, and unrelated parent secrets. Renderer closure has no lifecycle transition and cannot cancel main-process-owned validation.
   - **Visible result:** A deterministic conformance harness plays timeout, cancellation, shutdown, restart, start failure, non-zero exit, renderer close, and successful-exit scenarios and prints the resulting statuses/reasons.
   - **Durable records / external effects:** Defines serializable state and reason records. Filesystem test fixtures use a temporary directory and a link/junction escape where the host permits it; no child command is spawned.
   - **Failure / cancellation / restart:** Invalid canonical paths fail before a prepared command exists. Timeout, user cancellation, shutdown, and restart each end in `interrupted` with different reasons. Renderer closure is deliberately not a transition. A stopped step creates `PRIOR_STEP_STOPPED` records for later steps.
   - **Exact evidence:** Windows case/drive containment table; `..`, absolute, sibling-prefix, symlink, and junction escape tests; timeout table proving omission becomes 600 seconds, 1 and 3,600 seconds are accepted, 0 and 3,601 seconds are rejected, and the effective value appears in confirmation/snapshot output; fake-clock/process-control tests proving graceful whole-tree termination is requested first, force termination occurs only after five seconds and only for survivors, and later profile steps remain `not_run`; executable-resolution/PATHEXT table that asserts the resolved executable is recorded and no shell is requested; schema tests rejecting environment/secret fields; legal/illegal transition tests including renderer-window destruction as a no-op; restart fixture; exit-code truth table; assertion that no AI field can set status; environment policy fixture proving GitHub/AI credential names are excluded.
   - **Exit criterion:** AC-05, AC-06, AC-07, and AC-10 pass; F14 can implement the runner port without inventing status, timeout, cancellation, restart, credential, or working-directory behavior.

4. **Bound and redact output before it becomes evidence.**
   - **Blocked by:** Slice 3.
   - **Stories / requirements / acceptance criteria:** US-05-US-06; FR-05.1-FR-05.7; NFR-01; NFR-03; NFR-05; INV-04-INV-06; AC-08-AC-10.
   - **Implementation:** Add an incremental byte-oriented stream accumulator with independently enforced stdout and stderr retained-output limits. Version 1 fixes both the default and maximum at 1,048,576 bytes per stream per command; a profile may request a lower positive limit but cannot raise it. Retain equal head/tail portions where possible, original/retained byte counts, an explicit truncation marker, UTF-8-safe display decoding, ANSI/control normalization, and no unbounded retained copy. Add deterministic redaction for exact known-secret values and recognized sensitive assignments before any returned chunk is eligible for persistence, IPC, logging, display, or later AI context. Redaction failure returns `REDACTION_FAILURE` and non-passing evidence.
   - **Visible result:** Conformance fixtures show small output unchanged, oversized output with readable head/tail and a marker, and secret-bearing output with diagnostics preserved but values removed.
   - **Durable records / external effects:** Produces bounded/redacted evidence objects only. Raw fixture chunks exist only within individual test calls and are not written to snapshots or logs.
   - **Failure / cancellation / restart:** Chunk boundaries inside secrets, ANSI sequences, CRLF, and multi-byte UTF-8 are handled consistently. Any internal redaction failure prevents evidence from being labeled safe or passed.
   - **Exact evidence:** Schema/default tests proving stdout and stderr each default to 1,048,576 bytes, accept lower positive limits, and reject every higher value; independent-stream boundary tests at limit-1/limit/limit+1; randomized chunking test with identical output; UTF-8 split tests; head/tail accounting test; known-secret and case-insensitive sensitive-key corpus; negative test for ordinary diagnostic values; scan of serialized evidence proving raw secrets are absent.
   - **Exit criterion:** AC-08 and AC-09 pass; AC-10 remains true after output processing; the accumulator's retained memory is bounded by the configured stream limit plus fixed parser overhead.

5. **Record manual checks and the explicit no-safe-profile path.**
   - **Blocked by:** Slices 1-4.
   - **Stories / requirements / acceptance criteria:** US-07-US-08; FR-06.1-FR-06.5; NFR-02; NFR-05; INV-01-INV-02; INV-06-INV-07; AC-11-AC-12; application criteria APP-AC-39 and APP-AC-49.
   - **Implementation:** Add manual-attestation schemas tied to worktree/revision identity and `verified`, `failed`, or `not_run` outcomes. Add run-summary aggregation that preserves automated and manual evidence separately. Model absent, invalid, and confirmation-required profiles as completed `not_run` records rather than exceptions or empty success. Define consumer-facing warning data that remains attached to review/synchronization results and publication confirmation; the contract does not itself publish or block the separate explicit human decision.
   - **Visible result:** Fixture reports render **Verified manually**, **Manual check failed**, and **Not run** distinctly and show the exact remediation for `NO_PROFILE`, `CONFIRMATION_REQUIRED`, and `INVALID_PROFILE`.
   - **Durable records / external effects:** Defines serializable manual and no-run records. User identity is optional when the host cannot determine it; persistence/UI integration remains F03/F14/F16.
   - **Failure / cancellation / restart:** Missing user identity does not erase the timestamp or revision binding. Editing the worktree after attestation makes the attestation historical rather than silently current. Invalid/untrusted profiles never fall through to success.
   - **Exact evidence:** Manual outcome table; worktree revision-change test; aggregation matrix mixing automated and manual results; no-profile/confirmation/invalid fixtures; UI-copy contract test ensuring positive manual evidence never says **Test passed**; publication-warning serialization test.
   - **Exit criterion:** AC-11 and AC-12 pass; consumers can distinguish unavailable automation, failed automation, interruption, and human attestation without parsing prose.

6. **Freeze immutable run evidence and prove cross-workflow conformance.**
   - **Blocked by:** Slices 1-5.
   - **Stories / requirements / acceptance criteria:** US-01-US-08; FR-07.1-FR-07.3; NFR-02; NFR-04; INV-05; INV-08; AC-04; AC-13; all mapped application criteria.
   - **Implementation:** Add immutable snapshot creation/validation and a narrow consumer API used by future Review Bundle and Branch Synchronization orchestration. The API accepts resolved authorization and worktree identity, returns the complete pre-launch snapshot, and later aggregates only evidence matching that snapshot. Each serialized run and step explicitly records start/end timestamps, lifecycle state, machine-readable reason, executable, arguments, canonical working directory, resolved executable when available, exit code or signal when available, bounded/redacted stdout and stderr plus their byte/truncation metadata, and any applicable manual attestation. Add two thin test consumers representing review and synchronization; both must pass the same conformance suite and may not override source, trust, path, timeout, status, redaction, or aggregation rules. Document the handoff contracts for F01, F03, F14, F16, F18, and F23-F25.
   - **Visible result:** A conformance report demonstrates identical behavior for simulated review and synchronization consumers and links every F00 requirement to executable evidence.
   - **Durable records / external effects:** Commits JSON fixtures for valid/current and invalid/tampered snapshots plus the generated schema. No application database or external effect is introduced.
   - **Failure / cancellation / restart:** Mutation after snapshot creation, evidence with a mismatched snapshot ID, and unknown schema/reason values are rejected. Historical snapshots continue to parse after mutable source settings change.
   - **Exact evidence:** Snapshot round-trip and tamper tests; field-completeness test for every FR-07.2 run/step datum; mutable-settings-after-snapshot test; consumer contract tests run twice (review and synchronization); requirement-to-test traceability check; `npm run build`, `npm test`, and `npm run check`; both specification-linter workflows rerun against the final PRD/PLAN.
   - **Exit criterion:** AC-04 and AC-13 pass; FR-07.1-FR-07.3 and INV-08 have direct tests; all F00 acceptance criteria pass; downstream features can consume the package without redefining the contract.

## Cross-Slice Verification and Handoff

- The public package API remains deterministic and contains no imports from Electron, React, SQLite, Git, GitHub, or an AI provider.
- Test fixtures use synthetic secrets only. No developer credential, temporary linter API key, or local environment value is committed or printed.
- The generated JSON Schema is checked for drift in CI and is the checked-in interchange artifact; Zod remains the implementation source of truth.
- Root scripts are extended so clean-checkout build, tests, and checks include the new package without disturbing `tools/spec-linter`.
- F14 must reuse the conformance fixtures for real process-runner integration tests, including Windows process-tree termination and working-directory link/junction checks.
- F03 must persist the serialized contract without reinterpretation; unknown future versions fail closed and remain inspectable.
- F16 must render the contract-provided confirmation summary and warnings rather than rebuilding trust policy in the renderer.
- The top-level F00 checklist item remains unchecked until the implementation, conformance evidence, both specification-linter workflows, and required human product agreement are complete.
